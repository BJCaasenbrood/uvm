Projects, Locking and Activation

The files of a project

FileWritten byCommit it?Purpose
uvm.jsonyou, uvm init, uvm add, uvm removeYes What the project needs: dependencies with version ranges, toolboxes, MATLAB release. See the reference.
uvm.lockuvm lock, uvm syncYes What was picked: the exact commit of every package, including indirect ones.
.uvm/uvm syncNo (ignores itself) Local state; .uvm/paths.txt lists the folders that go on the path.

uvm finds the project by looking for uvm.json in the current folder and its parents, so commands work from any subfolder.

What uvm sync does

  1. Lock. If uvm.lock is missing, or the dependencies in uvm.json changed since it was written, the dependencies are resolved and the lock is rewritten. Otherwise the lock is used as it is.
  2. Install. Every locked commit that is not in the cache yet is fetched and unpacked.
  3. Check. uvm warns about missing toolboxes, unsupported MATLAB releases and functions defined by more than one package.
  4. Activate. The project's own folders and its packages go on the path.

Resolution

For each package, uvm picks the newest version tag that satisfies every package that asks for it, including indirect requirements. If my_analysis needs lib_b ^0.2 and lib_b 0.2.0 needs lib_a ^1.1, uvm installs the newest 1.x of lib_a, even if 2.0 exists.

When no single version fits, uvm stops with an error listing who requires what:

No version of "lib_a" satisfies all requirements:
  my_analysis requires lib_a ^2 (git@server:matlab/lib_a.git)
  lib_b requires lib_a ^1.1 (git@server:matlab/lib_a.git)

Locked versions are kept

Re-resolving does not upgrade packages behind your back. A package keeps its locked commit as long as it still satisfies the requirements, and in that case uvm does not even contact the server. Upgrade explicitly:

>> uvm sync --upgrade      % newest allowed versions of everything
>> uvm lock --upgrade      % same, but only rewrite uvm.lock

Dependencies that follow a branch are also pinned to the locked commit until you upgrade.

Activation and the path

uvm activate reads .uvm/paths.txt and adds those folders to the top of the path. It never resolves or downloads, so it is fast enough to run from startup.m. Only one project is active at a time: activating another project first removes the previous one's folders, and uvm deactivate removes them without activating anything.

The startup.m hook added by uvm setup runs uvm activate --quiet when MATLAB starts, which activates the project in the startup folder and does nothing if there is none. To activate another project later:

>> cd ~/work/other_project
>> uvm activate

MATLAB Projects

If you work with MATLAB Projects (.prj), let the project switch uvm environments for you:

>> uvm project            % in an existing uvm project
>> uvm init --project     % or when starting a new one

This creates a MATLAB project in the project root if there is none, and registers two files from resources/uvm/:

uvm_project_startup.mRuns when the project opens: syncs (normally just a quick check against uvm.lock) and activates. After a git pull that changed uvm.lock, opening the project installs the new versions.
uvm_project_shutdown.mRuns when the project closes: deactivates.

Commit resources/uvm/ along with the project file, so everyone who opens the project gets this behavior. Problems during opening become warnings (uvm:projectSyncFailed), so a project always opens. Undo it with uvm project --remove.

With MATLAB Projects you usually don't need the startup.m hook from uvm setup; you only need uvm itself on the path.

The cache

Everything downloaded lives in ~/.uvm, or in the folder named by the UVM_HOME environment variable:

git/One bare mirror per repository.
pkgs/<name>/<commit>/Installed packages, one folder per commit, shared by all projects.
config.jsonYour registries.

Installed folders never change after they are written. Several MATLAB sessions can share one cache: every download is written under a temporary name first and renamed when complete. uvm cache clean deletes the mirrors and packages (not your config); the next uvm sync downloads them again.
