Version Constraints

Versions are git tags

A package's versions are its tags of the form v1.2.3 or 1.2.3; v1.2 counts as 1.2.0. Other tags, including pre-releases like v2.0.0-rc1, are ignored. Both lightweight and annotated tags work.

Package constraints

The rules follow Cargo (Rust) and npm. Versions follow semantic versioning: a change in the first non-zero number is a breaking change.

ConstraintAllowsNote
^1.2.3>=1.2.3, <2.0.0Compatible updates. What uvm add writes.
1.2.3>=1.2.3, <2.0.0A bare version means ^.
^0.2.3>=0.2.3, <0.3.0Below 1.0, the minor number is the breaking one.
^0.0.3>=0.0.3, <0.0.4
~1.2.3>=1.2.3, <1.3.0Bug fixes only.
~1>=1.0.0, <2.0.0
>=1.2, >1.2, <2, <=2as written
=1.4.1exactly 1.4.1
>=1.2, <1.8bothCommas combine constraints.
*anything

On the command line, attach the constraint with @:

>> uvm add signal_utils@~1.4
>> uvm add 'signal_utils@>=1.2, <1.8'
>> uvm add signal_utils --version '>=1.2, <1.8'

Quote constraints that contain a comma or a space: in command syntax MATLAB treats a comma as the end of the statement.

MATLAB release constraints

The matlab field of uvm.json uses release names:

ConstraintAllows
>=R2023a or R2023aR2023a and newer
<R2025areleases before R2025a
>=R2022b, <R2025aR2022b up to R2024b

uvm warns (uvm:matlabRelease) when the running MATLAB falls outside the range of the project or any of its packages.
